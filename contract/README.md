# `contract/` — the rules implemented more than once

This is a monorepo with three languages: Java (`android/`), Python
(`server/comfy-node/`) and JavaScript/TypeScript (`reference/webgl-port/` and
`web/`). Several rules are implemented **more than once**, each copy claiming to
be the same rule, because the copies cannot share code across a language boundary
and (for the web port) across a deliberate decision to stop keeping it in sync.

They can share **bytes**. One golden fixture, each implementation tested against
it. That is the one thing a monorepo buys that three repositories cannot: the
copies are held together by a file rather than by a comment saying they agree.

Nothing here is generated by a test. `deph/generate.mjs` produces the PNG fixtures
and `splat/generate.mjs` captures the records, and both are checked in so a
fixture can be regenerated or explained — a test that rewrites its own expectation
can never fail.

## What is here

| contract | implementations | fixture | tested by |
|---|---|---|---|
| the tag rule | node `basrelief_depth/contract.py` (creates the filenames) + app `ComfyWorkflow.streamTag` (derives them) | `tag/cases.json` | `TagContractTest` (Java) · `test_contract.py` (Python) |
| the `dePH`/`dEPt` PNG chunk | app `:core/depth/DepthPng.java` + reference port `src/png-depth.js` + gallery `web/src/deph.ts` | `deph/*.png` + `deph/cases.json` | `DepthPngContractTest` (Java) · `png-depth.test.mjs` (Node) · `web/src/deph.test.ts` (TypeScript) |
| the splat sidecar | node writes it (`contract.py::splat_sidecar`) + app reads it (`:core/render/SplatSidecar.java`) + gallery reads it (`web/src/splat.ts`) | `sidecar/*.json` | `SidecarContractTest` (Java) · `test_contract.py` (Python) · `web/src/splat.test.ts` (TypeScript) |
| the `.splat` 32-byte record | app `:core/splat/SplatCloud.java` + gallery `web/src/splat.ts` | `splat/records.bin` + `splat/cases.json` | `SplatRecordContractTest` (Java) · `web/src/splat.test.ts` (TypeScript) |

**The record became a contract when it got a second reader.** This file used to say
it was deliberately not fixtured — `SplatCloudTest` pinned the layout field for
field and there was no second implementation to align with. That stopped being
true when the gallery grew a cloud renderer: `web/src/splat.ts` reads the same
bytes, and two copies that cannot share code need something to disagree about in
public. See *The `.splat` record* below.

## The tag rule

> Keep only the ASCII characters `[A-Za-z0-9_-]`, in order, then keep the first 48
> of them. Nothing is trimmed, normalised or replaced; an id that keeps nothing
> yields the empty string.

The prose this replaced — *"alnum plus `-`/`_`, truncated to 48"* — under-defined
two things, and the two copies had drifted on both:

1. **48 *what*.** Python truncated 48 **code points**; Java's `String.length()`
   counts **UTF-16 code units**, so an emoji counted twice — and a Java loop that
   stops at 48 units can stop *between* a surrogate pair, leaving a lone surrogate
   in a filename. The fixture case is 47 ASCII, an emoji, then 10 ASCII: Python
   answered 47 ASCII + the emoji, Java answered 47 ASCII + half an emoji.
2. **Which "alnum".** Python's `str.isalnum()` accepts Unicode categories L\* **and
   N\***; `Character.isLetterOrDigit` is L\* plus **Nd only**. So `Ⅷ` (Nl) and `²`
   (No) survived the node and were dropped by the app. A supplementary-plane letter
   (Deseret `𐐀`, Lo) is one `isalnum()` character in Python and two non-letter
   surrogates in Java's `char` loop.

**The rule is now ASCII on both sides.** Every kept character is one byte, one
UTF-16 unit and one code point, so "48" needs no unit of its own and none of the
above is representable. That costs nothing a real id needs: ids are UUIDs, and the
rule exists for a hand-edited index, where the only requirement is that both sides
produce the **same name**, not that any particular character survives.

**Which side changed: both, and neither was right.** The node is authoritative
because it creates the files, but its rule was not a decision — it was Python's
`isalnum()` typed into a docstring that *called* it "alnum" without defining it.
There is no reason for a filename alphabet to include superscripts, and there is
one strong reason against: a Unicode filename has no canonical spelling across
NFC/NFD. So the alphabet was narrowed at the source and the Java copy was rewritten
from `Character.isLetterOrDigit` to an explicit ASCII set. `nodes.py` no longer
holds a copy at all (its `MoGeGeometryNPZ` held a second one); it imports
`contract.py`.

**What a wrong answer looks like:** the app asks the server for
`basrelief_<tag>_depth.mp4` and it is not there. The run has finished; the files
are on disk under a name one character different. Nothing errors on either side —
the fetch 404s, the import retries, and the user sees "failed" for a run that
succeeded. The `names` block in `tag/cases.json` is what pins the filenames, not
just the tag, because that is the consequence.

**The rule is not injective, and that is accepted rather than hidden:** two ids can
sanitise to one tag (`a b` and `a/b` both give `ab`), so two concurrent runs for
colliding ids would target the same output filenames. Ids are UUIDs in production,
where a collision cannot happen; making the names collision-free would require
something the app cannot derive (a per-run nonce), which is exactly what the
"address a run you never saw a response for" property forbids. The rule's job is a
deterministic, filesystem-safe name that BOTH sides agree on — not uniqueness.

## The `dePH` chunk

A PNG carries its depth in an ancillary chunk named `dePH` (or `dEPt`), case-
insensitive. The payload is either a **complete PNG** (self-describing) or **exactly
`width*height` bytes of raw 8-bit grey**, whose dimensions come from the outer
`IHDR` — so a raw payload placed before `IHDR` claims nothing and is refused.

`deph/cases.json` states, per file: `status` (`ok` / `not-png` /
`no-depth-chunk` / `bad-payload`), `form` (`raw` / `png`), the dimensions and the
SHA-256 of the depth payload. The payload bytes are deliberately unlike the outer
image's pixels, so an implementation that returns the **colour** image where the
depth belongs fails the digest instead of passing with a plausible picture.

**What a wrong answer looks like:** the photo has relief on the phone and is flat
on the web (or the reverse), with no error anywhere. Both accept the file; they
disagree only about whether it carries depth. The refused fixtures are half the
contract for the same reason — "wrong-size payload" must be *refused*, because
accepting it means rendering a depth map whose dimensions were guessed.

The APIs are deliberately not identical: JS returns an error code and Java
returns `null` for every refusal, because the app only ever asks "is there depth
here". The JS test pins the exact code; the Java test pins the refusal.

The TypeScript copy (`web/src/deph.ts`) is the third and chooses per consumer:
it returns the error code like the JS port, and the payload the way Java does —
either raw grey plus the outer IHDR's dimensions, or the whole PNG plus its own
dimensions. The gallery needs both dimension pairs to refuse a depth map that is
not the photo's size (`whole-png.png` is 3×2 under an 8×6 photo, and the app
layer refuses to stretch it). It never re-encodes the payload: raw grey stays
raw grey, and a whole-PNG payload is passed through byte-for-byte.

## The `.splat` record

A cloud is a sequence of 32-byte little-endian records, and each record is
**exactly the two `RGBA32UI` texels the renderer uploads**:

| offset | field | the texel word it becomes |
|---|---|---|
| 0 | `x` float32 | texel A, `.x` |
| 4 | `y` float32 | texel A, `.y` |
| 8 | `z` float32 | texel A, `.z` |
| 12 | `sx` float32 | texel A, `.w` |
| 16 | `sy` float32 | texel B, `.x` |
| 20 | `sz` float32 | texel B, `.y` |
| 24 | `r,g,b,a` uint8 | texel B, `.z` — the little-endian word |
| 28 | `w,x,y,z` quaternion uint8 (`q*128+128`) | texel B, `.w` — the little-endian word |

**The colour word must not be read as a float, and that is what the fixture is
for.** Four `uint8` in an `RGBA32F` texel are one float, and for an opaque bright
splat that float is a **NaN**: the word is `r | g<<8 | b<<16 | a<<24`, so its
exponent is `((a & 0x7F) << 1) | (b >> 7)` and it is all-ones when `a` is 127 or
255 and `b >= 128`. The old WebGL prototype uploads `RGBA32F` (see
`.design/prototype/ab/3d/splatline/`), and desktop GPUs preserve a NaN's payload so
it renders perfectly there; **Mali canonicalises it**, so `floatBitsToUint` hands
the shader a canonical NaN instead of those bytes and the splat draws flat white.
Measured on the device, that was the grey speckle over a sky while the tan sand
beside it stayed pixel-perfect. Integers cannot be canonicalised, so the record is
uploaded verbatim as `RGBA32UI` and unpacked with integer shifts.

The fixture carries four records captured from
`android/app/src/main/res/raw/demo.splat` by `splat/generate.mjs`, chosen for their
KINDS rather than their indices, and each one states why it is there:

| record | what it pins |
|---|---|
| `first` | an ordinary splat whose baked opacity (alpha 43) makes the quad **shrink** (`sqrt(2 ln 43)/3 = 0.914`), with a quaternion far from identity, so the decode and the rotation are both exercised |
| `bright` | an opaque bright splat whose colour word **is a NaN as a float32** — the case the float path destroys. 16,964 of the demo cloud's 149,504 records are this case |
| `opaque` | alpha 255, mid-file: the alpha-extent clip is the **identity** (`sqrt(2 ln 255) = 3.33 > 3`), the other end of the range |
| `padding` | 32 zero bytes, which is how the node pads a budget out — a real cloud therefore ENDS in them, and they must decode without throwing and be culled (`z > 0`), not divided by |

**What a wrong answer looks like:** the cloud renders, and the bright regions are
white or grey speckle with no error anywhere — or, for the other three records, a
cloud whose tail reads past the buffer, whose quads are half-size, or whose
colours are swapped with its rotations. None of those is visible in a screenshot
of a mid-tone subject.

## The splat sidecar

`basrelief_<tag>.splat.json` is written once by the node and read by the app and by
the gallery. It carries **three** numbers the readers use — `focal`, `width`,
`height` — reduced to the dimensionless lens `focal / height`. The gallery uses
the same three and the same reduction (`web/src/splat.ts`, asserted against this
fixture), because a cloud's screen size is proportional to the focal it was
reconstructed through and a lens in pixels is meaningless on a frame the browser
decoded at a different size.

**What a wrong answer looks like:** a missing `focal` read as `0` and divided
through, or an absent `height` treated as a number. The cloud then draws through a
0-degree camera (nothing visible) or the run is failed over a number a look does
not need. `0` is the node's own "the fit failed" answer; `0`, absent and unreadable
are all **"no claim"** — the caller draws the default look — never a value to
invert. `sidecar/cases.json` names each of those, and the `splat-sidecar.json`
golden is the full eleven-field body the node writes.

## Running the tests

**Java** (`:core`; the gate is `android/podman-build.sh test`):

```
cd android && ./podman-build.sh test
```

The test working directory is `android/core`, while the fixtures are at the
repository root, so the directory is passed in as the **`basrelief.contract`
system property** from `android/core/build.gradle` rather than hard-coded as a
`../../` chain. The build container mounts only `android/` at `/workspace`, so
`podman-build.sh` also mounts `./contract` at `/contract` — which is exactly where
that property resolves when the build root's parent is `/`.

**Python** (a container; the host is not expected to have Python, and ComfyUI,
torch and numpy are not needed):

```
podman run --rm -v "$PWD:/w:ro" -w /w python:3.12-slim \
    python3 server/comfy-node/tests/test_contract.py
```

**JavaScript** (plain Node — `png-depth.js` uses no browser API):

```
node contract/deph/png-depth.test.mjs
```

**TypeScript** (the gallery's copies; plain Node type stripping — no browser, no
test framework, no install beyond the app's own dependencies):

```
cd web && pnpm test
```

That one command runs three files: `src/deph.test.ts` (the packed PNG),
`src/media.test.ts` (the media vocabulary) and `src/splat.test.ts` (the record, the
camera, the lens and the sort).

CI runs all four: the JS check and the TypeScript check (in the `web-app` job),
the Java check inside the `android` job's `test` step, and the Python one in its
own `python-contract` job (there was no Python job at all before this directory
existed).

## Adding a fixture

1. Put the bytes (or the JSON) here and the expectation in a `cases.json` beside
   them, with a `why` — a fixture without a stated failure mode is a number
   nobody can judge.
2. Add the read to every implementation's test. A fixture only one side reads is
   not a contract; it is a test of one copy.
3. Prefer a case that would pass a plausible wrong implementation. "One byte too
   many is refused" and "an absent focal is not zero" exist because the wrong
   answers there look fine on screen.
4. If the fixture's hardest case can be LOST by a regeneration, `check-parity.mjs`
   should hold it by name — `splat/cases.json`'s four records are asserted there
   for that reason, as the tag table's hard rows are in `TagContractTest`.
